# Optional backend and collaboration

Phase 4 adds an optional FastAPI + SQLite service. Start it with `python3 apps/api/run.py` (or `npm run api`) after installing `apps/api/requirements.txt`. The runner reads `API_HOST` and `API_PORT`, defaulting to `0.0.0.0:8020`. The API is available at `http://localhost:8020`; the database defaults to `apps/data/swar_sadhak.db` (a relative `DATABASE_URL` resolves against `apps/`); set `DATABASE_URL` to change it.

Schema changes are ordered migrations in `apps/api/app/db.py` (`MIGRATIONS`), tracked with SQLite `PRAGMA user_version`. Each one runs once, in its own transaction, on API start. Append new migrations; never edit or reorder applied ones.

Accounts are created only by an Owner (`/api/owner/users`) or by the `create-owner` CLI command; there is no public registration. Users can hold several roles (`owner`, `teacher`, `student`) in `user_roles`. Passwords are PBKDF2-hashed. Tokens are HMAC-signed, expire after one hour, and carry the user's `token_version`; a password, role or active-status change increments it, which revokes older tokens. Five failed sign-ins for one username within 15 minutes return 429 until the window passes (in-process memory, so it resets on restart). There is no OAuth or email recovery. Never use the default secret for deployment.

Batches (`/api/teacher/batches`) are weekly recurring classes. Each batch belongs to one course the teacher teaches, stores wall-clock `HH:MM` start and end times in the academy timezone (`GET /api/academy`), a weekday bitmask, and a `starts_on` date. Members must be actively enrolled with that teacher in that course (403 otherwise). An active batch that overlaps another of the same teacher's active batches returns 409 with the conflicting batches; touching times (10:00–11:00 next to 11:00–12:00) are allowed. Members who already have another active batch at that time come back as `warnings` that name the other batch but never its teacher. Other teachers' batches return 404. The Owner can list every batch at `/api/owner/batches` but cannot edit them. Students read their own timetable at `GET /api/student/batches`: batch name, course, teacher name, days, times, start date and status, only for batches backed by an active enrollment, and never other members.

Students own their derived practice summaries and can read assigned routines/assignments. Teachers can manage only their own routines and assign them only to students. The Owner is not a teaching role: routine and assignment writes require the `teacher` role. Ownership and role checks are enforced by the API, not the frontend. There are no public profiles, leaderboards, chat, or unrestricted teacher access.

The web app remains local-first. `VITE_API_URL` is optional; missing or unavailable API responses are reported as local-only/sync-failed and do not remove local sessions or block microphone analysis. Practice sync accepts derived metrics only and rejects extra raw-audio fields. No PCM samples, browser cookies, or API keys are stored. Recordings are stored only when a student deliberately attaches one to an assignment answer, as described below.

Assignments (`/api/teacher/assignments`, `/api/student/assignments`) are manual Riyaz tasks: a teacher gives a title, instructions, an optional due date and files or links to chosen students actively enrolled with them in one course. Each student answers once (`draft`, then `submitted`; the teacher marks it `reviewed` with feedback). Drafts are private to the student. Students who have submitted cannot be removed from the assignment. The older `/api/assignments` routes, which link a synced practice routine to one student, are unchanged.

Files live in private object storage behind presigned URLs; `app/storage.py` signs SigV4 URLs with the standard library, so there is no SDK dependency. Two backends speak the same protocol. `local` (the default) keeps files under `apps/data/storage/` (`STORAGE_DIR`) and serves them from this API at path-style URLs `/storage/<bucket>/<key>` that accept only presigned requests: the signature, method, signed `Content-Type` and expiry are checked as R2 checks them, and GET supports byte ranges for audio/video seeking. `r2` uses a Cloudflare R2 bucket through its S3 API. It is selected automatically when the four `R2_*` variables are set, or explicitly with `STORAGE_BACKEND`. The rest of the app, and the browser, cannot tell the two apart. `API_PUBLIC_URL` (default `http://localhost:8020`) is the address browsers use to reach the local store. Uploads: `POST /api/files/uploads` checks access, type and size (audio 25 MB, video 300 MB, PDF 20 MB, images 10 MB; 10 attachments per assignment or answer) and returns a 15-minute PUT URL; the browser uploads directly; `POST /api/files/{id}/complete` checks the stored size and type and deletes the object if they differ. `GET /api/files/{id}` returns a one-hour download URL after an access check (404 otherwise). `POST /api/files/links` adds an `https://` link instead of a file. Deleting an assignment deletes its files from R2 first; if storage is unreachable the API returns 502 and deletes nothing. Unconfirmed uploads older than a day are removed when the next upload starts.

To use R2, set `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` and `R2_BUCKET` in `apps/api/.env`, which is read at start; real environment variables win. The bucket needs a CORS rule that allows `PUT`, `GET` and `HEAD` with the `Content-Type` header from the web app's origin. `python3 apps/api/run.py check-storage` uploads, downloads and deletes a test file through presigned URLs on either backend; for `local` the API must be running. If `STORAGE_BACKEND=r2` is set without credentials, uploads return 503 and links still work. Local files are not backed up automatically, so back up `apps/data/` with the database.
